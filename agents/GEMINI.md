GEMINI.md — 完全自律で「Windows/Mac 両対応」アプリを完成させるための改善指示書
目的: 本プロジェクトの既存コードと仕様を読み取り、人手の操作（承認/質問/待機）を極力ゼロで、設計 → 実装 → テスト → バグ修正 まで自律的に完遂すること。

対象アプリ: 「アダアフィ用ショート動画支援アプリ（仮）」：

機能A: XのRT監視 → スクショ → 背景動画合成 → ショート動画自動生成/保存

機能B: TikTok/YouTube のショート監視 → 転載向けフォーマットへ変換/保存

UI: ダッシュボード（監視状況と開始/設定ボタン）、設定（監視対象/間隔、動画出力：解像度・長さ・BGM・背景・上/下テロップ）

0. 自律実行ポリシー（最重要）
絶対に守るルール

起動と復元: 常に --yolo --checkpointing で起動する。破壊的変更の直前にスナップショットを作成し、失敗時は自動で最新のスナップショットを復元して続行する。

意思決定: 確認ダイアログは禁止。不明点は合理的な仮定に基づいて進め、その意思決定プロセスをログに記録する。

開発サイクル: 「計画 → 実装 → テスト → 修正」の短いサイクルを自律的に反復実行する。テスト失敗時は、原因を分析して自動修正し、再度テストを実行する。

エラーハンドリング:

連続失敗: 3回の連続失敗で計画を再立案する。10回失敗した場合はスコープを縮小（ユニットテスト中心へ移行）し、それでも解決しない場合は直前のスナップショットへロールバックする。

ネットワークエラー: APIレートリミット（429）、アクセス拒否（403）、その他ネットワーク切断が発生した場合は、指数バックオフ（例：2s, 4s, 8s… 最大5分）によるリトライを実施する。タイムアウトや長時間の回線断は待機モードへ移行し、接続回復後に自動でタスクを再開する。

ロギング: ログは機械可読な JSON Lines 形式と、人間が読みやすいUIログの2系統で出力する。

言語: すべてのチャット（エージェント応答、計画出力、エラーメッセージ）およびREADME、ログの説明は日本語で行う。コードや設定ファイル内の固有名詞は英語を許容する。

UI/UX: ダッシュボードから監視の開始/停止が可能であり、設定画面での変更がアプリケーションの動作にリアルタイムで反映される。

機能安定性: 機能A（X）および機能B（TikTok/YouTube）の監視、処理、保存の一連のジョブが、連続して安定稼働する。

出力品質: 動画出力は指定されたスキーマ（解像度、長さ、フォーマット等）を満たし、ダミーデータを用いたテストで正常に出力されることを確認する。

テストカバレッジ: ユニットテスト、統合テスト、E2Eテストのすべてがローカル環境およびCI環境で成功する。

2. 改善タスク一覧
2.1. コードベースの全体レビュー
目的: プロジェクト全体のアーキテクチャ、依存関係、および既存のコード品質を完全に把握する。

指示:

すべてのソースコードファイル（.py, .js, .html, .css等）を読み込み、クラス、関数、モジュール間の関連性を解析する。

特に動画生成、API連携、UI制御に関連するロジックを重点的に確認する。

潜在的な問題点（非効率な処理、エラーハンドリングの欠如など）を特定し、ログに記録する。

2.2. 動画生成機能の修正（TikTok, YouTube）
目的: 現在失敗しているX以外のプラットフォーム（TikTok, YouTube）からの動画生成を正常化する。

指示:

原因分析: 各プラットフォーム（TikTok, YouTube）の動画生成処理が失敗する根本原因を特定する。ログ、エラーメッセージ、および関連コードを詳細に調査する。

※Xを含むすべての動画サイトの監視対象IDは設定済みのため、その監視対象IDを使用する。

コード修正: 特定した原因に基づき、動画のダウンロード、フォーマット変換、保存処理のコードを修正・改善する。各プラットフォームの仕様変更やAPIの制約に対応できているか確認する。

リファクタリング: Xの動画生成ロジックと共通化できる部分を特定し、コードの重複を排除して保守性を向上させる。

2.3. 統合テストと自律的デバッグサイクル
目的: すべての動画生成機能が、仕様通りに安定して動作することを保証する。

指示:

テストケースの生成: X, TikTok, YouTubeのそれぞれについて、正常系（動画が正しく生成・保存される）のテストケースを作成する。

自律的テスト実行: 作成したテストケースを自動で実行する。

デバッグループ:

テストが失敗した場合、関連するログとソースコードを分析し、修正パッチを自動生成して適用する。

修正後、再度テストを実行する。

すべてのプラットフォームの動画生成テストが成功するまで、この「テスト→分析→修正」のサイクルを自律的に繰り返す。

最終検証: すべてのテストが成功したことを確認し、ログに完了レポートを出力してタスクを終了する。

3. 総合機能テスト
目的: 上記の改善とテストが完了した後、アプリケーション全体のワークフローが仕様通りに動作することを保証する。

指示:

この指示書および元の仕様通りに実装されているか、網羅的にテストを実施する。

4. 実行シナリオ（エージェントの行動計画）
[開始] 2.1. コードベースの全体レビュー を実行。

[分析・修正] 2.2. 動画生成機能の修正 を実行。

[テスト・デバッグ] 2.3. 統合テストと自律的デバッグサイクル を実行。すべての動画生成が成功するまでループ。

[最終確認] 3. 総合機能テスト を実行。

[完了] すべてのテストが正常に終了し、各プラットフォームの動画が正常に生成されたのを確認して終了する。

最後に
この指示書は「人手ゼロで走り切る」ための改善計画です。ここに記したルールと順序で、計画→実装→テスト→ビルドを自律反復し、完了基準の達成をもって終了してください。
